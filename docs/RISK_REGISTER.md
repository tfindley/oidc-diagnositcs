## Treatment key

| Code                            | Meaning                                                                    |
| ------------------------------- | -------------------------------------------------------------------------- |
| **FIXED**                       | Vulnerability eliminated — package removed or patched                      |
| **ACCEPTED — NOT APPLICABLE**   | Vulnerable code path is not present or reachable in this application       |
| **ACCEPTED — NO FIX AVAILABLE** | No Debian stable fix exists; vendor/upstream has not released a patch      |
| **ACCEPTED — DISPUTED**         | Upstream maintainer disputes severity or classifies as non-vulnerability   |
| **ACCEPTED — LOCAL ONLY**       | Exploitable only by a local authenticated user; not reachable from network |
| **ACCEPTED — BUILD-TIME ONLY**  | Vulnerability is in a build tool; the package is not present at runtime    |

## Application design risks

These are architectural / design-level risks introduced by the application itself, distinct from container CVEs. They were added when the session storage model moved from client-side signed cookies to server-side encrypted-filesystem ("zero-knowledge sessions") to support providers like EntraID whose claim sets exceed the 4 KB cookie limit.

| Risk ID | Risk                                                                                                  | Treatment                                                                                                                                                                                                                                                                                                                                                       |
| ------- | ----------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| R-A-01  | Session ciphertext on disk readable by host root, container escape, volume mount, or backup leak     | **MITIGATED.** Ciphertext requires both the user's per-session key (cookie-only) **and** the server pepper to decrypt. Neither half alone yields plaintext. Operators may set `SESSION_FILE_DIR` to a tmpfs mount if even ciphertext exposure is unacceptable. Sessions on disk become unreadable past their `SESSION_LIFETIME_MINUTES` TTL via Fernet's TTL check. |
| R-A-02  | `SESSION_ENCRYPTION_PEPPER` leaked via debug tracebacks, debug REPL, or process env introspection    | **ACCEPTED — operational control.** `FLASK_DEBUG=false` is mandated for production (documented in [SECURITY.md](../SECURITY.md)). Pepper rotation invalidates all active sessions, which is the intended emergency-revocation lever.                                                                                                                            |
| R-A-03  | Active server compromise (RCE on the running app) decrypts in-flight session plaintext during request handling | **ACCEPTED.** The defence scope is passive read / data-at-rest, not RCE. Mitigated separately by container hardening (non-root `app` user, no shell in default cmd, network policies). An RCE attacker on the cookie-based predecessor design would have been equally able to read tokens.                                                                       |
| R-A-04  | Cookie theft grants an attacker the per-session key for that one user                                | **ACCEPTED.** Cookie possession = identity, same threat model as any web session. Mitigated by `HttpOnly`, `Secure` (when behind HTTPS), and `SameSite=Lax` flags on the session cookie.                                                                                                                                                                         |
| R-A-05  | Session disk usage grows unbounded if sessions are abandoned mid-flow (never cleared by logout)       | **PARTIALLY MITIGATED.** Abandoned sessions become unreadable once Fernet's TTL elapses, but the file remains until deleted. Recommend a periodic prune of `*.sess` files older than `SESSION_LIFETIME_MINUTES` for long-running deployments. Container restart clears them when `SESSION_FILE_DIR` is on `/tmp` or a tmpfs.                                     |
| R-A-06  | JWTs decoded and displayed without signature verification                                            | **ACCEPTED — by design.** This is a diagnostic tool; the JWT-decoder use case explicitly inspects malformed or third-party tokens. Documented in [SECURITY.md](../SECURITY.md) "Intended use". JWKS-based verification is exposed as a separate, opt-in feature on the JWT decoder page.                                                                          |
